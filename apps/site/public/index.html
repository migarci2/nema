nema

your learning state, everywhere.

The web teaches. Your vault remembers. Your agent connects the two.

nema is a WebMCP protocol for learning, plus five pages that implement it. A vault you own holds signed evidence of what you have learned and derives your state from it, per concept and per ability. Websites never read the vault: they ask one question, and the vault answers with the smallest true answer, after you approve it. Nothing else leaves.

01

How it works

four objects, three roles, one browser
  1. 1 LearningManifest

    A provider publishes what a unit teaches, what it assumes, and what evidence each activity can produce. Your agent reads it before you commit a single minute.

  2. 2 ReadinessAssertion

    The agent asks your vault. The vault stops and shows you a modal, and only after you approve does it sign a token bound to that one audience, valid for 30 minutes, carrying bands and nothing else.

  3. 3 EvidenceReceipt

    You do the work in the provider's page. The grader runs on its server, the provider signs a receipt, your agent carries it back, and the vault recomputes your bands from the ledger.

  4. 4 LearningNeed

    The vault turns the ledger into what to do next, with the rubric attached, so a coach can run the exercise without inventing the standard.

04

Privacy you can see

the token does not exist until you click

Disclosure, as the vault renders it

A ReadinessAssertion carries only the concepts that were requested, as status bands, plus an audience, a purpose, a request hash and an expiry. That key set is fixed by the spec and asserted by a unit test.

  • Minimal. Three lines were asked for, three lines are shared. Nothing else is in the payload.
  • Audience bound. Valid at one origin. Presented anywhere else it fails with wrong-audience.
  • Short lived. 30 minutes, no refresh. The agent asks again and you approve again.
  • Unlinkable by default. learnerKeyId is derived from your vault key and the audience, so two providers see different ids for the same person.
  • Refusable. Deny returns { status: 'denied' }, writes nothing, and the disclosure ledger records nothing, because nothing was disclosed.

05

What nema refuses to do

the absence is the security model

Tools that do not exist on any nema surface

NameWhy it does not exist
set_masterystate is derived from signed evidence, never written
get_full_historydisclosure is per request and per audience, never bulk
submit_answer_for_learneronly the human answers, and grading runs server side
disable_reviewthe schedule is a property of the evidence, not a setting
export_vaultexport is a button a human clicks, not an agent capability

This is not a policy written in a prompt. Prompts can be argued with, missing functions cannot. Verify it yourself on any nema page: call await document.modelContext.getTools() and read the list.

06

Why WebMCP

the substrate, not a detail

WebMCP changes the shape of the problem.

A site declares what it can do as tools on the page it already serves, and any agent in the browser can call them while the person watches.

No accounts, no shared database, no server that sees both sides.

Five origins in this demo, and any sixth one can join by registering five tools and publishing a public key. WebMCP is the substrate where a protocol like this is just pages, and where the human stays in the loop by construction, because the approval is a modal on the page the data belongs to.

07

For judges

three minutes, sixty seconds if you are behind

Browser setupnothing needs an account or an API key

  • ChatGPT desktop. The in-app browser has WebMCP on by default. Open the vault in it and the tools are discovered with no setup.
  • Chrome 149 or later. Go to chrome://flags/#enable-webmcp-testing, set it to Enabled, restart, then open the coach.
  • Any other browser. Every page loads the Chrome Labs WebMCP polyfill, so tools register and the UI behaves identically. The header pill says how many tools are live.
