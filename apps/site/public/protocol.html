Architecture

nema runs as static pages on seven separate origins. There is no shared database, no account system and no server that sees both sides of a handoff. Each page is served by a Cloudflare Worker; the two providers also keep a Worker route at /api/*, because grading and signing happen on the server and neither the answer key nor the issuer private key may reach the browser.

OriginRoleWhat it holds
nema.migarci2.dev hub this reference, the judge guide, the philosophy. Two tools of its own.
nema-vault.migarci2.dev vault the learner's receipts, goals and key, in localStorage. 11 imperative tools plus one declarative form.
saucier.migarci2.dev provider Saucier School: the unit pan-sauces-foundations, a deterministic grader, the issuer key saucier-2026-09.
linecook.migarci2.dev provider Line Cook Lab: the unit service-under-pressure, a deterministic grader, the issuer key linecook-2026-09.
maillard.migarci2.dev provider Maillard, explained: one blog post installed with the embed, self certified receipts, no server.
aesgcm.migarci2.dev provider frereit's AES-GCM article under CC BY-SA 4.0, republished with the embed, beside the original and the generated diff.
cpu.migarci2.dev provider Lexi Mattick's CPU chapter under the MIT licence, republished with the embed, beside the original and the generated diff.

Tools are registered with document.modelContext.registerTool on the page that owns the data, so whichever agent the reader brought discovers them there and nowhere else. Native end to end tests ran on Chrome for Testing 154. nema targets WebMCP enabled Chrome 149+ and ChatGPT's in app browser. Other browsers use the bundled Chrome Labs polyfill for a degraded demonstration.

The MCP bridge

packages/nema-mcp is the same vault behind a stdio MCP server, for terminal agents. It imports apps/vault/public/vault.js and the same TOOLS array rather than reimplementing anything, backs localStorage with ~/.nema/vault.json, and asks for consent through MCP elicitation. If the client cannot elicit, the tool returns denied with the command that pre-approves that audience, so the agent still cannot approve on its own. The same eleven imperative tools, same names, same schemas, same return shapes: browser agents reach the vault through WebMCP, terminal agents reach it through MCP, and the vault does not know the difference. The declarative form exists only in the browser. 

claude mcp add nema -- node /path/to/nema/packages/nema-mcp/bin.mjs
codex  mcp add nema -- node /path/to/nema/packages/nema-mcp/bin.mjs

The six objects

Concept, registry entry, unsigned

The shared vocabulary, from shared/concepts.json, 34 ids in this build. Providers map their own ids onto it with aliases, keyed by the app directory that owns them (harness is Saucier School, security is Line Cook Lab), so a provider can join the registry without renaming anything of its own.

What a unit teaches, what it assumes, and what evidence each activity can produce. This is the object that lets an agent plan before the learner commits. Activity type is one of lesson, diagnostic, interactive-lab, free-recall.

skipIf is a list of { concept, ability, status }. The activity is skipped when every entry is satisfied by the assertion: verified satisfies verified, and verified or uncertain satisfies uncertain. onlyIf has the same shape and includes an activity only when every entry matches the assertion status exactly. It exists for diagnostics that are only worth running when a requirement came back uncertain.

ReadinessRequest, unsigned, provider to vault, carried by the agent

{
  "protocol": "nema/0.1",
  "audience": "https://saucier.migarci2.dev",
  "purpose": "personalize-pan-sauces-path",
  "requirements": [ { "concept": "nema:knife-skills", "ability": "apply" } ]
}

requestHash = sha256(JSON.stringify(request)), formatted as "sha256:" + hex. The vault copies it into the assertion so the disclosure can be tied back to the exact question that was asked.

ReadinessAssertion, signed by the vault

{
  "type": "readiness-assertion",
  "protocol": "nema/0.1",
  "audience": "https://saucier.migarci2.dev",
  "purpose": "personalize-pan-sauces-path",
  "requestHash": "sha256:6b1f...",
  "learnerKeyId": "lk_Qm9wS2pMbk4xR3Zq",
  "assertions": [
    { "concept": "nema:knife-skills", "ability": "apply", "status": "verified", "confidence": "high" },
    { "concept": "nema:ratios", "ability": "apply", "status": "uncertain", "confidence": "low" }
  ],
  "issuedAt": "2026-09-02T10:00:00Z",
  "expiresAt": "2026-09-02T10:30:00Z",
  "vaultKey": { "kty": "EC", "crv": "P-256", "x": "...", "y": "..." }
}
  • The assertion is self certifying. The verifier uses the embedded vaultKey. There is no directory of learners to look anything up in.
  • learnerKeyId = "lk_" + b64url(sha256bytes(vaultKey.x + "|" + audience)).slice(0, 16). The same learner is a different id at every provider, and no provider can compute another provider's id.
  • The assertion carries only the concepts the request asked for. No history, no dates of study, no attempt counts, no other subjects, no misconceptions, no review schedule, no provider history.
  • Lifetime is 30 minutes. There is no refresh: the agent asks again, and the learner approves again.

  • subject is the learnerKeyId the provider learned from the assertion, so a receipt is not a global identifier either.

Token format

Every signed object travels as one compact string, short enough for an agent to carry in its context without mangling it. 

nema1.<b64url(payloadJson)>.<b64url(signature)>
  • payloadJson is the exact UTF-8 JSON produced by the builder, keys in the order this reference lists them.
  • The signature is ECDSA on P-256 with SHA-256, raw r || s, over the UTF-8 bytes of that exact payload string.
  • Verification never re-serializes. It verifies the decoded payload string as transmitted, then parses it. Two implementations that disagree about key order still interoperate.
  • b64url is base64url without padding.
export const PROTOCOL = 'nema/0.1';
encodeToken(payloadObj, signatureB64url) -> string
decodeToken(token) -> { payload, payloadString, signature }   // throws on malformed
await signToken(payloadObj, privateJwk) -> string
await verifyToken(token, publicJwk) -> { ok, payload, reason? }

Measured against the reference builders, a token is about 950 to 1150 characters: a three requirement ReadinessAssertion is around 1100, an EvidenceReceipt with one claim around 980 and with two claims around 1125. The embedded vaultKey and the contentHash dominate the payload, so size grows slowly with the number of claims. That is small enough to travel in an agent's context and large enough that a model should not be asked to retype it, which is why the vault and every provider render each token in a textarea with a Copy button, so a human can complete the handoff if the agent damages the string.

Verification rules

A provider verifying a ReadinessAssertion

verifyAssertion(token, { audience, now }) returns { ok, payload, reason }. Every step in order, first failure wins.

  • decodeToken succeeds, else malformed.
  • payload.type === 'readiness-assertion' and payload.protocol === 'nema/0.1', else malformed.
  • Signature verifies against payload.vaultKey, else bad-signature.
  • payload.audience equals the verifier's own origin, else wrong-audience.
  • payload.expiresAt > now, else expired.

Nothing else is trusted, and a provider must not treat a missing concept as a failure. What a provider may keep: the latest assertion payload, as its own session state, so the page can redraw the personalized path on reload. The reference providers store it in localStorage under nema.<app>.v1. What a provider must not do: forward the token to anyone, use the payload after expiresAt, or present it to another audience as a credential. It is a statement addressed to one origin at one moment, not a bearer token for the learner.

A vault verifying an EvidenceReceipt

verifyReceipt(token, issuerMap, { seenReceiptIds }), where issuerMap maps keyId to { origin, jwk, name, id }.

  • decodeToken succeeds, else malformed.
  • payload.type === 'evidence-receipt', else malformed.
  • issuers[payload.keyId] exists and its origin equals payload.issuer, else unknown-issuer. The receipt is stored with status pending, changes no state, and stays visible in the ledger.
  • Signature verifies against the issuer JWK, else bad-signature. Rejected.
  • payload.receiptId has not been seen before, else duplicate. Rejected.

Only receipts that pass all five become verified and feed the derivation. shared/issuers.json maps a short name to { kid, jwk }; the seed issuer maps to origin urn:nema:seed and the name "nema demo seed", so demo evidence is labelled as such in the ledger and never pretends to come from a real provider.

Derivation

The vault stores evidence, never state. Pure functions in shared/inference.js recompute every band from the ledger on each read, so the same receipts always produce the same bands and any observer can reproduce them.

Weights

The vault owns these numbers. Providers declare which grader produced a claim; they do not declare how much it counts.

GraderWeightMeaning
deterministic1.0machine checkable answer key
provider-rubric0.8provider rubric applied to free text
agent-assessed0.6an agent judged the answer against a vault rubric
self-report0.3the learner says so
exposure0.1the learner read or watched the material

Score and band

  • A claim contributes to its own ability and to every lower ability on the ladder recognize < retrieve < explain < apply < transfer. discriminate is a side ability and its claims contribute only to discriminate.
  • resultValue: passed 1, partial 0.5, failed -0.5. recency = exp(-daysSince / 60). value = weight(grader) * resultValue * recency, and score is their sum.
  • Bands: durable at 1.6, usable at 0.9, fragile at 0.4, uncertain above 0, otherwise unknown.
  • If the best grader weight for an ability is exposure, the band is capped at uncertain, and exposure evidence never counts as a pass, so it never schedules or postpones a review.
  • Memory: stabilityDays = min(60, 3 * 2 ** (passes - 1)), nextReview = lastSuccess + stabilityDays, and a failed claim after a success resets stability to 3 days.

A provider never sees a score. It sees the assertion status: durable and usable report as verified, fragile and uncertain report as uncertain, and unknown reports as missing.

Needs

computeNeeds(state, { concepts, goals, misconceptions, now, budgetMinutes }).

KindTriggerUrgency
retrievea review is due at or above retrieve0.6 to 1, by how overdue
applyexplain is usable or better and apply is fragile or worse0.7
discriminatethe concept has a confusableWith pair, is applied or explained well, and has no discrimination evidence0.65
acquirea goal lists the concept, or a prereq of one, and every ability is unknown0.5

priority = urgency * goalRelevance / max(2, minutes), where goalRelevance is 1.5 inside an active goal, 1.2 for a prereq of one, else 1. With a budgetMinutes the needs are taken greedily in priority order until the budget is full, which is why a five minute review can return a discriminate need rather than the concept you know least.

Tool catalogs

Vault role

Eleven imperative tools, plus one declarative form (set_learning_goal_form), so getTools() lists twelve. Every result is a JSON object with a status field.

ToolInputReturns
get_vault_summary {} { status:'ok', concepts, durable, usable, fragile, uncertain, reviewsDue, goals, receipts, pendingReceipts, disclosures }
get_learner_state { concepts?: string[] } { status:'ok', state:[{ concept, title, bands, nextReview, reviewDue }] }
set_learning_goal { title, concepts: string[] } { status:'ok', goalId }
create_readiness_assertion { audience, purpose, requirements:[{concept, ability}] } { status:'approved', token, expiresAt, shared, withheld }
stage_evidence_receipt { token } { status:'accepted', receiptId, issuer, issuerName, activity, claims, changes, reviewsScheduled }
get_learning_needs { budgetMinutes?: number } { status:'ok', budgetMinutes, needs: LearningNeed[] }
record_agent_assessment { needId, rubricResults:[{ criterion, met }], learnerAnswerSummary } { status:'accepted', receiptId, result, changes }
get_disclosure_ledger {} { status:'ok', disclosures:[{ audience, purpose, requestHash, sharedAt, expiresAt, shared, withheld }] }
get_evidence_ledger { limit?: number } { status:'ok', receipts:[{ receiptId, issuerName, activity, claims, grader, signature, receivedAt, effect }] }
propose_concept_alignment { origin, providerConcept, concept, relation, rationale } { status:'proposed', alignmentId, alignment }
get_concept_alignments { origin?: string } { status:'ok', alignments:[{ alignmentId, origin, providerConcept, concept, relation, status, proposedBy, rationale }] }
  • get_learner_state returns bands. Never scores, never receipts, never dates of study. Its description says so, because the agent reads descriptions.
  • create_readiness_assertion opens the consent modal and blocks until the human decides. It returns { status:'denied' } on Deny and { status:'timeout' } after 120 seconds. There is no auto approve by default; the modal offers one hour for one provider as an explicit choice.
  • stage_evidence_receipt returns pending with reason unknown-issuer, or rejected with reason bad-signature, duplicate or malformed.
  • propose_concept_alignment only asks. The alignment lands in the vault as proposed, and nothing is translated until the learner confirms it on the page. There is no tool that confirms one, on either surface.
  • record_agent_assessment writes a receipt with grader: 'agent-assessed', weight 0.6, no signature, reported as signature: 'agent' and rendered with the "agent assessed" badge. It rejects a needId the vault did not issue, so an agent cannot invent an assessment for an exercise that never happened.

Provider role

Both demo providers implement the same five imperative tools plus the declarative present_assertion form, so getTools() lists six. There is one difference in the second one: Saucier School personalizes a path; Line Cook Lab checks prerequisites and unlocks labs.

ToolInputReturns
describe_learning_offer {} { status:'ok', manifest }
personalize_learning_path { assertionToken } { status:'personalized', learnerKeyId, requirements, path, skipped, fullMinutes, personalMinutes }
check_prerequisites { assertionToken } { status:'checked', recognized, unlocked, locked, recommendedFirst, skippable }

Rejection reasons for the assertion tools are exactly the verification reasons: bad-signature, wrong-audience, expired, malformed. Signing happens server side: POST /api/receipt re-grades the submission with the same grader the browser used, returns 422 { status:'not-passed' } if it does not pass, and otherwise signs with env.ISSUER_PRIVATE_JWK. GET /api/manifest returns the manifest for anyone with curl.

68, 27, 21

The demo learner has knife skills and heat control evidenced, and only weak evidence about ratios. Saucier School offers 68 minutes. After one approved disclosure it offers 27, and after the learner passes the six minute ratios diagnostic, keeps the receipt and presents a fresh assertion, it offers 21. Nothing is ever added to the path: everything that survives was already inside the 68 minute offer.

Struck throughMinutesReason shown in the page
heat-control-primer12skipped: heat-control explain verified
knife-skills-refresher15skipped: knife-skills apply verified
ratios-primer14skipped: ratios apply uncertain, diagnostic instead

ratios-diagnostic survives the first cut because its onlyIf matches ratios.apply at exactly uncertain, which is what onlyIf is for. A cook with no evidence about ratios at all would keep the 14 minute primer instead and drop the diagnostic. Once the diagnostic is passed and its receipt is staged, ratios.apply moves to verified, the onlyIf no longer matches, and 27 becomes 21.

Line Cook Lab is the other half of the claim. It has never spoken to Saucier School. It verifies one signature from the vault, checks the token was minted for its own origin, reads the bands it asked for, skips the material already covered, and names the prerequisite still missing. Once that prerequisite is supplied, its labs open with the label "Prerequisite recognised from another provider".

Conformance

Ten checks. The reference implementation runs 1 to 6 as unit tests under npm test and 7 to 10 by hand in the browser during the demo.

  1. Token roundtrip. signToken then verifyToken returns ok: true. Flipping one byte of the payload returns ok: false.
  2. Audience binding. An assertion minted for provider A is rejected by provider B with reason wrong-audience.
  3. Expiry. An assertion whose expiresAt is in the past is rejected with reason expired, even with a valid signature.
  4. Unknown issuer. A receipt signed by a key that is not in issuers.json returns { status: 'pending', reason: 'unknown-issuer' }, is visible in the ledger, and changes no band.
  5. Replay. Staging the same receiptId twice returns { status: 'rejected', reason: 'duplicate' } and changes no band.
  6. Minimal disclosure. For any request, the assertion payload contains only the fixed key set above, and assertions contains only concepts present in the request.
  7. Derivation. The seeded ledger produces the documented bands. Adding a passing ratios.apply receipt moves that band from uncertain to usable, and the vault shows the change.
  8. Human gate. create_readiness_assertion returns no token until a human clicks Approve. Denying returns { status: 'denied' } and writes nothing.
  9. No answer path. document.modelContext.getTools() on a provider page contains no tool that accepts an answer, and issue_evidence_receipt returns { status: 'not-passed' } until the grader has passed the activity.
  10. Visible effect. Every tool call changes something on screen and appears in the page's tool activity strip with its name and duration.

Forbidden tools

These names must not exist on any nema surface. Their absence is the security model.

NameWhy it does not exist
set_masterystate is derived from signed evidence, never written
get_full_historyhistory stays in the vault; disclosure is per request and per audience
submit_answer_for_learneronly the human answers; the agent has no path to the grader
disable_reviewthe schedule is a property of the evidence, not a setting
export_vaultexport is a button the human clicks, not a capability an agent can call

A conformant vault fails conformance if any tool it registers can write a band directly, return raw receipts to an unbounded audience, or produce an assertion without a human decision.
