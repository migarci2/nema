while writing this article was how <em>simple</em> computers are. It’s still hard for me not to psych myself out, expecting more complexity or abstraction than actually exists! If there’s one thing you should burn into your brain before continuing, it’s that everything that seems simple actually is that simple. This simplicity is very beautiful and sometimes very, very cursed.</p><p>Let’s start with the basics of how your computer works at its very core.</p><h2 id="how-computers-are-architected">How Computers Are Architected</h2><p>The <em>central processing unit</em> (CPU) of a computer is in charge of all computation. It’s the big cheese. The shazam alakablam. It starts chugging as soon as you start your computer, executing instruction after instruction after instruction.</p><p>The first mass-produced CPU was the <a href="http://www.intel4004.com/" rel="noopener noreferrer" target="_blank">Intel 4004</a>, designed in the late 60s by an Italian physicist and engineer named Federico Faggin. It was a 4-bit architecture instead of the <a href="https://en.wikipedia.org/wiki/64-bit_computing" rel="noopener noreferrer" target="_blank">64-bit</a> systems we use today, and it was far less complex than modern processors, but a lot of its simplicity does still remain.</p><p>The “instructions” that CPUs execute are just binary data: a byte or two to represent what instruction is being run (the opcode), followed by whatever data is needed to run the instruction. What we call <em>machine code</em> is nothing but a series of these binary instructions in a row. <a href="https://en.wikipedia.org/wiki/Assembly_language" rel="noopener noreferrer" target="_blank">Assembly</a> is a helpful syntax for reading and writing machine code that’s easier for humans to read and write than raw bits; it is always compiled to the binary that your CPU knows how to read.</p><img src="images/assembly-to-machine-code-translation.png" loading="eager" style="max-width: 400px;" alt="A diagram demonstrating how machine code translates to assembly and back. A bidirectional arrow connects three examples: Machine Code (Binary) followed by 3 bytes of binary numbers, Machine Code (Hex) followed by those 3 bytes translated to hex (0x83, 0xC3, 0x0A), and Assembly followed by &quot;add ebx, 10&quot;. The Assembly and Machine Code are color-coded so it is clear that each byte of the machine code translate to one word in the assembly." width="935" height="505"/><blockquote><p>An aside: instructions aren’t always represented 1:1 in machine code as in the above example. For example, <code>add eax, 512</code> translates to <code>05 00 02 00 00</code>.</p><p>The first byte (<code>05</code>) is an opcode specifically representing <em>adding the EAX register to a 32-bit number</em>. The remaining bytes are 512 (<code>0x200</code>) in <a href="https://en.wikipedia.org/wiki/Endianness" rel="noopener noreferrer" target="_blank">little-endian</a> byte order.</p><p>Defuse Security created <a href="https://defuse.ca/online-x86-assembler.htm" rel="noopener noreferrer" target="_blank">a helpful tool</a> for playing around with the translation between assembly and machine code.</p></blockquote><p>RAM is your computer’s main memory bank, a large multi-purpose space which stores all the data used by programs running on your computer. That includes the program code itself as well as the code at the core of the operating system. The CPU always reads machine code directly from RAM, and code can’t be run if it isn’t loaded into RAM.</p><p>The CPU stores an <em>instruction pointer</em> which points to the location in RAM where it’s going to fetch the next instruction. After executing each instruction, the CPU moves the pointer and repeats. This is the <em>fetch-execute cycle</em>.</p><img src="images/fetch-execute-cycle.png" loading="lazy" style="max-width: 360px; margin: 0 auto;" alt="A diagram demonstrating the fetch-execute cycle. There are two bubbles of text. The first is labeled &quot;Fetch&quot; and has the text &quot;Read instruction from memory at the current instruction pointer.&quot; The second is titled &quot;Execute&quot; and has the text &quot;Run the instruction and then move the instruction pointer.&quot; The fetch bubble has an arrow pointing to the execute bubble, and the execute bubble has an arrow pointing back to the fetch bubble, implying a repeated process." width="848" height="458"/><p>After executing an instruction, the pointer moves forward to immediately after the instruction in RAM so that it now points to the next instruction. That’s why code runs! The instruction pointer just keeps chugging forward, executing machine code in the order in which it has been stored in memory. Some instructions can tell the instruction pointer to jump somewhere else instead, or jump different places depending on a certain condition; this makes reusable code and conditional logic possible.</p><p>This instruction pointer is stored in a <a href="https://en.wikipedia.org/wiki/Processor_register" rel="noopener noreferrer" target="_blank"><em>register</em></a>. Registers are small storage buckets that are extremely fast for the CPU to read and write to. Each CPU architecture has a fixed set of registers, used for everything from storing temporary values during computations to configuring the processor.</p><p>Some registers are directly accessible from machine code, like <code>ebx</code> in the earlier diagram.</p><p>Other registers are only used internally by the CPU, but can often be updated or read using specialized instructions. One example is the instruction pointer, which can’t be read directly but can be updated with, for example, a jump instruction.</p><h2 id="processors-are-naive">Processors Are Naive</h2><p>Let’s go back to the original question: what happens when you run an executable program on your computer? First, a bunch of magic happens to get ready to run it — we’ll work through all of this later — but at the end of the process there’s machine code in a file somewhere. The operating system loads this into RAM and instructs the CPU to jump the instruction pointer to that position in RAM. The CPU continues running its fetch-execute cycle as usual, so the program begins executing!</p><p>(This was one of those psyching-myself-out moments for me — seriously, this is how the program you are using to read this article is running! Your CPU is fetching your browser’s instructions from RAM in sequence and directly executing them, and they’re rendering this article.)</p><img src="images/instruction-pointer.png" loading="lazy" style="max-width: 400px;" alt="A diagram depicting a series of bytes of machine code in RAM. A highlighted byte is pointed to by an arrow labeled &quot;Instruction Pointer,&quot; and there are arrows representing how the instruction pointer moves forward in RAM." width="935" height="372"/><p>It turns out CPUs have a super basic worldview; they only see the current instruction pointer and a bit of internal state. Processes are entirely operating system abstractions, not something CPUs natively understand or keep track of.</p><p><em>*waves hands* processes are abstractions made up by <del>os devs</del> big byte to sell more computers</em></p><p>For me, this raises more questions than it answers:</p><ol><li>If the CPU doesn’t know about multiprocessing and just executes instructions sequentially, why doesn’t it get stuck inside whatever program it’s running? How can multiple programs run at once?</li><li>If programs run directly on the CPU, and the CPU can directly access RAM, why can’t code access memory from other processes, or, god forbid, the kernel?</li><li>Speaking of which, what’s the mechanism that prevents every process from running any instruction and doing anything to your computer? AND WHAT’S A DAMN SYSCALL?</li></ol><p>The question about memory deserves its own section and is covered in <a href="https://cpu.land/the-translator-in-your-computer">chapter 5</a> — the TL;DR is that most memory accesses actually go through a layer of misdirection that remaps the entire address space. For now, we’re going to pretend that programs can access all RAM directly and computers can only run one process at once. We’ll explain away both of these assumptions in time.</p><p>It’s time to leap through our first rabbit hole into a land filled with syscalls and security rings.</p><blockquote><p><strong>Aside: what is a kernel, btw?</strong></p><p>Your computer’s operating system, like macOS, Windows, or Linux, is the collection of software that runs on your computer and makes all the basic stuff work. “Basic stuff” is a really general term, and so is “operating system” — depending on who you ask, it can include such things as the apps, fonts, and icons that come with your computer by default.</p><p>The kernel, however, is the core of the operating system. When you boot up your computer, the instruction pointer starts at a program somewhere. That program is the kernel. The kernel has near-full access to your computer’s memory, peripherals, and other resources, and is in charge of running software installed on your computer (known as userland programs). We’ll learn about how the kernel has this access — and how userland programs don’t — over the course of this article.</p><p>Linux is just a kernel and needs plenty of userland software like shells and display servers to be usable. The kernel in macOS is called <a href="https://en.wikipedia.org/wiki/XNU" rel="noopener noreferrer" target="_blank">XNU</a> and is Unix-like, and the modern Windows kernel is called the <a href="https://en.wikipedia.org/wiki/Architecture_of_Windows_NT" rel="noopener noreferrer" target="_blank">NT Kernel</a>.</p></blockquote><h2 id="two-rings-to-rule-them-all">Two Rings to Rule Them All</h2><p>The <em>mode</em> (sometimes called privilege level or ring) a processor is in controls what it’s allowed to do. Modern architectures have at least two options: kernel/supervisor mode and user mode. While an architecture might support more than two modes, only kernel mode and user mode are commonly used these days.</p><p>In kernel mode, anything goes: the CPU is allowed to execute any supported instruction and access any memory. In user mode, only a subset of instructions is allowed, I/O and memory access is limited, and many CPU settings are locked. Generally, the kernel and drivers run in kernel mode while applications run in user mode.</p><p>Processors start in kernel mode. Before executing a program, the kernel initiates the switch to user mode.</p><img src="images/kernel-mode-vs-user-mode.png" loading="lazy" style="max-width: 500px; margin: 0 auto;" alt="Two fake iMessage screenshots demonstrating the different between user and kernel mode protections. The first, labeled Kernel Mode: right side says &quot;Read this protected memory!&quot;, left side replies &quot;Here you go, dear :)&quot;. The second, labeled User Mode: right side says &quot;Read this protected memory!&quot;, left side replies &quot;No! Segmentation fault!&quot;" width="1072" height="433"/><p>An example of how processor modes manifest in a real architecture: on x86-64, the current privilege level (CPL) can be read from a register called <code>cs</code> (code segment). Specifically, the CPL is contained in the two <a href="https://en.wikipedia.org/wiki/Bit_numbering" rel="noopener noreferrer" target="_blank">least significant bits</a> of the <code>cs</code> register. Those two bits can store x86-64’s four possible rings: ring 0 is kernel mode and ring 3 is user mode. Rings 1 and 2 are designed for running drivers but are only used by a handful of older niche operating systems. If the CPL bits are <code>11</code>, for example, the CPU is running in ring 3: user mode.</p><h2 id="what-even-is-a-syscall">What Even is a Syscall?</h2><p>Programs run in user mode because they can’t be trusted with full access to the computer. User mode does its job, preventing access to most of the computer — but programs need to be able to access I/O, allocate memory, and interact with the operating system <em>somehow</em>! To do so, software running in user mode has to ask the operating system kernel for help. The OS can then implement its own security protections to prevent programs from doing anything malicious.</p><p>If you’ve ever written code that interacts with the OS, you’ll probably recognize functions like <code>open</code>, <code>read</code>, <code>fork</code>, and <code>exit</code>. Below a couple of layers of abstraction, these functions all use <em>system calls</em> to ask the OS for help. A system call is a special procedure that lets a program start a transition from user space to kernel space, jumping from the program’s code into OS code.</p><p>User space to kernel space control transfers are accomplished using a processor feature called <a href="https://en.wikipedia.org/wiki/Interrupt#Software_interrupts" rel="noopener noreferrer" target="_blank"><em>software interrupts</em></a>:</p><ol><li>During the boot process, the operating system stores a table called an <a href="https://en.wikipedia.org/wiki/Interrupt_vector_table" rel="noopener noreferrer" target="_blank"><em>interrupt vector table</em></a> (IVT; x86-64 calls this the <a href="https://en.wikipedia.org/wiki/Interrupt_descriptor_table" rel="noopener noreferrer" target="_blank">interrupt descriptor table</a>) in RAM and registers it with the CPU. The IVT maps interrupt numbers to handler code pointers.</li></ol><img src="images/interrupt-vector-table.png" loading="lazy" style="max-width: 300px; margin: 0 auto;" alt="A image of a table captioned &quot;Interrupt Vector Table&quot;. The first column, labeled with a number sign, has a series of numbers starting at 01 and going to 04. The corresponding second column of the table, labeled &quot;Handler Address&quot;, contains a random 8-byte-long hex number per entry. The bottom of the table has the text &quot;So on and such forth...&quot;" width="555" height="463"/><ol start="2"><li>Then, userland programs can use an instruction like <a href="https://www.felixcloutier.com/x86/intn:into:int3:int1" rel="noopener noreferrer" target="_blank">INT</a> which tells the processor to look up the given interrupt number in the IVT, switch to kernel mode, and then jump the instruction pointer to the memory address stored in the IVT.</li></ol><p>When this kernel code finishes, it uses an instruction like <a href="https://www.felixcloutier.com/x86/iret:iretd:iretq" rel="noopener noreferrer" target="_blank">IRET</a> to tell the CPU to switch back to user mode and return the instruction pointer to where it was when the interrupt was triggered.</p><p>(If you were curious, the interrupt ID used for system calls on Linux is <code>0x80</code>. You can read a list of Linux system calls on <a href="https://man7.org/linux/man-pages/man2/syscalls.2.html" rel="noopener noreferrer" target="_blank">Michael Kerrisk’s online manpage directory</a>.)</p><h3 id="wrapper-apis-abstracting-away-interrupts">Wrapper APIs: Abstracting Away Interrupts</h3><p>Here’s what we know so far about system calls:</p><ul><li>User mode programs can’t access I/O or memory directly. They have to ask the OS for help interacting with the outside world.</li><li>Programs can delegate control to the OS with special machine code instructions like INT and IRET.</li><li>Programs can’t directly switch privilege levels; software interrupts are safe because the processor has been preconfigured <em>by the OS</em> with where in the OS code to jump to. The interrupt vector table can only be configured from kernel mode.</li></ul><p>Programs need to pass data to the operating system when triggering a syscall; the OS needs to know which specific system call to execute alongside any data the syscall itself needs, for example, what filename to open. The mechanism for passing this data varies by operating system and architecture, but it’s usually done by placing data in certain registers or on the stack before triggering the interrupt.</p><p>The variance in how system calls are called across devices means it would be wildly impractical for programmers to implement system calls themselves for every program. This would also mean operating systems couldn’t change their interrupt handling for fear of breaking every program that was written to use the old system. Finally, we typically don’t write programs in raw assembly anymore — programmers can’t be expected to drop down to assembly any time they want to read a file or allocate memory.</p><img src="images/syscall-architecture-differences.png" loading="lazy" style="max-width: 650px; margin: 0 auto;" alt="A drawing captioned &quot;System calls are implemented differently across architectures.&quot; On the left is a smiling CPU receiving some binary and spitting out a filename, file.txt. Separated on the right is a different CPU receiving the same binary data but with a confused and nauseous facial expression." width="1057" height="360"/><p>So, operating systems provide an abstraction layer on top of these interrupts. Reusable higher-level library functions that wrap the necessary assembly instructions are provided by <a href="https://www.gnu.org/software/libc/" rel="noopener noreferrer" target="_blank">libc</a> on Unix-like systems and part of a library called <a href="https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/libraries-and-headers" rel="noopener noreferrer" target="_blank">ntdll.dll</a> on Windows. Calls to these library functions themselves don’t cause switches to kernel mode, they’re just standard function calls. Inside the libraries, assembly code does actually transfer control to the kernel, and is a lot more platform-dependent than the wrapping library subroutine.</p><p>When you call <code>exit(1)</code> from C running on a Unix-like system, that function is internally running machine code to trigger an interrupt, after placing the system call’s opcode and arguments in the right registers/stack/whatever. Computers are so cool!</p><h2 id="the-need-for-speed--lets-get-cisc-y">The Need for Speed / Let’s Get CISC-y</h2><p>Many <a href="https://en.wikipedia.org/wiki/Complex_instruction_set_computer" rel="noopener noreferrer" target="_blank">CISC</a> architectures like x86-64 contain instructions designed for system calls, created due to the prevalence of the system call paradigm.</p><p>Intel and AMD managed not to coordinate very well on x86-64; it actually has <em>two</em> sets of optimized system call instructions. <a href="https://www.felixcloutier.com/x86/syscall.html" rel="noopener noreferrer" target="_blank">SYSCALL</a> and <a href="https://www.felixcloutier.com/x86/sysenter" rel="noopener noreferrer" target="_blank">SYSENTER</a> are optimized alternatives to instructions like <code>INT 0x80</code>. Their corresponding return instructions, <a href="https://www.felixcloutier.com/x86/sysret.html" rel="noopener noreferrer" target="_blank">SYSRET</a> and <a href="https://www.felixcloutier.com/x86/sysexit" rel="noopener noreferrer" target="_blank">SYSEXIT</a>, are designed to transition quickly back to user space and resume program code.</p><p>(AMD and Intel processors have slightly different compatibility with these instructions. <code>SYSCALL</code> is generally the best option for 64-bit programs, while <code>SYSENTER</code> has better support with 32-bit programs.)</p><p>Representative of the style, <a href="https://en.wikipedia.org/wiki/Reduced_instruction_set_computer" rel="noopener noreferrer" target="_blank">RISC</a> architectures tend not to have such special instructions. AArch64, the RISC architecture Apple Silicon is based on, uses only <a href="https://developer.arm.com/documentation/ddi0596/2021-12/Base-Instructions/SVC--Supervisor-Call-" rel="noopener noreferrer" target="_blank">one interrupt instruction</a> for syscalls and software interrupts alike. I think Mac users are doing fine :)</p><hr/><p>Whew, that was a lot! Let’s do a brief recap:</p><ul><li>Processors execute instructions in an infinite fetch-execute loop and don’t have any concept of operating systems or programs. The processor’s mode, usually stored in a register, determines what instructions may be executed. Operating system code runs in kernel mode and switches to user mode to run programs.</li><li>To run a binary, the operating system switches to user mode and points the processor to the code’s entry point in RAM. Because they only have the privileges of user mode, programs that want to interact with the world need to jump to OS code for help. System calls are a standardized way for programs to switch from user mode to kernel mode and into OS code.</li><li>Programs typically use these syscalls by calling shared library functions. These wrap machine code for either software interrupts or architecture-specific syscall instructions that transfer control to the OS kernel and switch rings. The kernel does its business and switches back to user mode and returns to the program code.</li></ul><p>Let’s figure out how to answer my first question from earlier:</p><blockquote><p>If the CPU doesn’t keep track of more than one process and just executes instruction after instruction, why doesn’t it get stuck inside whatever program it’s running? How can multiple programs run at once?</p></blockquote><p>The answer to this, my dear friend, is also the answer to why Coldplay is so popular… clocks! (Well, technically timers. +<p>The one thing that surprised me over and over again while writing this article was how <em>simple</em> computers are. It’s still hard for me not to psych myself out, expecting more complexity or abstraction than actually exists! If there’s one thing you should burn into your brain before continuing, it’s that everything that seems simple actually is that simple. This simplicity is very beautiful and sometimes very, very cursed.</p><p>Let’s start with the basics of how your computer works at its very core.</p><h2 id="how-computers-are-architected">How Computers Are Architected</h2><p>The <em>central processing unit</em> (CPU) of a computer is in charge of all computation. It’s the big cheese. The shazam alakablam. It starts chugging as soon as you start your computer, executing instruction after instruction after instruction.</p><p>The first mass-produced CPU was the <a href="http://www.intel4004.com/" rel="noopener noreferrer" target="_blank">Intel 4004</a>, designed in the late 60s by an Italian physicist and engineer named Federico Faggin. It was a 4-bit architecture instead of the <a href="https://en.wikipedia.org/wiki/64-bit_computing" rel="noopener noreferrer" target="_blank">64-bit</a> systems we use today, and it was far less complex than modern processors, but a lot of its simplicity does still remain.</p><p>The “instructions” that CPUs execute are just binary data: a byte or two to represent what instruction is being run (the opcode), followed by whatever data is needed to run the instruction. What we call <em>machine code</em> is nothing but a series of these binary instructions in a row. <a href="https://en.wikipedia.org/wiki/Assembly_language" rel="noopener noreferrer" target="_blank">Assembly</a> is a helpful syntax for reading and writing machine code that’s easier for humans to read and write than raw bits; it is always compiled to the binary that your CPU knows how to read.</p><img src="images/assembly-to-machine-code-translation.png" loading="eager" style="max-width: 400px;" alt="A diagram demonstrating how machine code translates to assembly and back. A bidirectional arrow connects three examples: Machine Code (Binary) followed by 3 bytes of binary numbers, Machine Code (Hex) followed by those 3 bytes translated to hex (0x83, 0xC3, 0x0A), and Assembly followed by &quot;add ebx, 10&quot;. The Assembly and Machine Code are color-coded so it is clear that each byte of the machine code translate to one word in the assembly." width="935" height="505"/><blockquote><p>An aside: instructions aren’t always represented 1:1 in machine code as in the above example. For example, <code>add eax, 512</code> translates to <code>05 00 02 00 00</code>.</p><p>The first byte (<code>05</code>) is an opcode specifically representing <em>adding the EAX register to a 32-bit number</em>. The remaining bytes are 512 (<code>0x200</code>) in <a href="https://en.wikipedia.org/wiki/Endianness" rel="noopener noreferrer" target="_blank">little-endian</a> byte order.</p><p>Defuse Security created <a href="https://defuse.ca/online-x86-assembler.htm" rel="noopener noreferrer" target="_blank">a helpful tool</a> for playing around with the translation between assembly and machine code.</p></blockquote><p>RAM is your computer’s main memory bank, a large multi-purpose space which stores all the data used by programs running on your computer. That includes the program code itself as well as the code at the core of the operating system. The CPU always reads machine code directly from RAM, and code can’t be run if it isn’t loaded into RAM.</p><p>The CPU stores an <em>instruction pointer</em> which points to the location in RAM where it’s going to fetch the next instruction. After executing each instruction, the CPU moves the pointer and repeats. This is the <em>fetch-execute cycle</em>.</p><img src="images/fetch-execute-cycle.png" loading="lazy" style="max-width: 360px; margin: 0 auto;" alt="A diagram demonstrating the fetch-execute cycle. There are two bubbles of text. The first is labeled &quot;Fetch&quot; and has the text &quot;Read instruction from memory at the current instruction pointer.&quot; The second is titled &quot;Execute&quot; and has the text &quot;Run the instruction and then move the instruction pointer.&quot; The fetch bubble has an arrow pointing to the execute bubble, and the execute bubble has an arrow pointing back to the fetch bubble, implying a repeated process." width="848" height="458"/><p>After executing an instruction, the pointer moves forward to immediately after the instruction in RAM so that it now points to the next instruction. That’s why code runs! The instruction pointer just keeps chugging forward, executing machine code in the order in which it has been stored in memory. Some instructions can tell the instruction pointer to jump somewhere else instead, or jump different places depending on a certain condition; this makes reusable code and conditional logic possible.</p><p>This instruction pointer is stored in a <a href="https://en.wikipedia.org/wiki/Processor_register" rel="noopener noreferrer" target="_blank"><em>register</em></a>. Registers are small storage buckets that are extremely fast for the CPU to read and write to. Each CPU architecture has a fixed set of registers, used for everything from storing temporary values during computations to configuring the processor.</p><p>Some registers are directly accessible from machine code, like <code>ebx</code> in the earlier diagram.</p><p>Other registers are only used internally by the CPU, but can often be updated or read using specialized instructions. One example is the instruction pointer, which can’t be read directly but can be updated with, for example, a jump instruction.</p>
+<!-- nema: retrieval question --><nema-activities for="architecture-check"></nema-activities>
+<h2 id="processors-are-naive">Processors Are Naive</h2><p>Let’s go back to the original question: what happens when you run an executable program on your computer? First, a bunch of magic happens to get ready to run it — we’ll work through all of this later — but at the end of the process there’s machine code in a file somewhere. The operating system loads this into RAM and instructs the CPU to jump the instruction pointer to that position in RAM. The CPU continues running its fetch-execute cycle as usual, so the program begins executing!</p><p>(This was one of those psyching-myself-out moments for me — seriously, this is how the program you are using to read this article is running! Your CPU is fetching your browser’s instructions from RAM in sequence and directly executing them, and they’re rendering this article.)</p><img src="images/instruction-pointer.png" loading="lazy" style="max-width: 400px;" alt="A diagram depicting a series of bytes of machine code in RAM. A highlighted byte is pointed to by an arrow labeled &quot;Instruction Pointer,&quot; and there are arrows representing how the instruction pointer moves forward in RAM." width="935" height="372"/><p>It turns out CPUs have a super basic worldview; they only see the current instruction pointer and a bit of internal state. Processes are entirely operating system abstractions, not something CPUs natively understand or keep track of.</p><p><em>*waves hands* processes are abstractions made up by <del>os devs</del> big byte to sell more computers</em></p><p>For me, this raises more questions than it answers:</p><ol><li>If the CPU doesn’t know about multiprocessing and just executes instructions sequentially, why doesn’t it get stuck inside whatever program it’s running? How can multiple programs run at once?</li><li>If programs run directly on the CPU, and the CPU can directly access RAM, why can’t code access memory from other processes, or, god forbid, the kernel?</li><li>Speaking of which, what’s the mechanism that prevents every process from running any instruction and doing anything to your computer? AND WHAT’S A DAMN SYSCALL?</li></ol><p>The question about memory deserves its own section and is covered in <a href="https://cpu.land/the-translator-in-your-computer">chapter 5</a> — the TL;DR is that most memory accesses actually go through a layer of misdirection that remaps the entire address space. For now, we’re going to pretend that programs can access all RAM directly and computers can only run one process at once. We’ll explain away both of these assumptions in time.</p><p>It’s time to leap through our first rabbit hole into a land filled with syscalls and security rings.</p><blockquote><p><strong>Aside: what is a kernel, btw?</strong></p><p>Your computer’s operating system, like macOS, Windows, or Linux, is the collection of software that runs on your computer and makes all the basic stuff work. “Basic stuff” is a really general term, and so is “operating system” — depending on who you ask, it can include such things as the apps, fonts, and icons that come with your computer by default.</p><p>The kernel, however, is the core of the operating system. When you boot up your computer, the instruction pointer starts at a program somewhere. That program is the kernel. The kernel has near-full access to your computer’s memory, peripherals, and other resources, and is in charge of running software installed on your computer (known as userland programs). We’ll learn about how the kernel has this access — and how userland programs don’t — over the course of this article.</p><p>Linux is just a kernel and needs plenty of userland software like shells and display servers to be usable. The kernel in macOS is called <a href="https://en.wikipedia.org/wiki/XNU" rel="noopener noreferrer" target="_blank">XNU</a> and is Unix-like, and the modern Windows kernel is called the <a href="https://en.wikipedia.org/wiki/Architecture_of_Windows_NT" rel="noopener noreferrer" target="_blank">NT Kernel</a>.</p></blockquote>

+<h2 id="two-rings-to-rule-them-all">Two Rings to Rule Them All</h2><p>The <em>mode</em> (sometimes called privilege level or ring) a processor is in controls what it’s allowed to do. Modern architectures have at least two options: kernel/supervisor mode and user mode. While an architecture might support more than two modes, only kernel mode and user mode are commonly used these days.</p><p>In kernel mode, anything goes: the CPU is allowed to execute any supported instruction and access any memory. In user mode, only a subset of instructions is allowed, I/O and memory access is limited, and many CPU settings are locked. Generally, the kernel and drivers run in kernel mode while applications run in user mode.</p><p>Processors start in kernel mode. Before executing a program, the kernel initiates the switch to user mode.</p><img src="images/kernel-mode-vs-user-mode.png" loading="lazy" style="max-width: 500px; margin: 0 auto;" alt="Two fake iMessage screenshots demonstrating the different between user and kernel mode protections. The first, labeled Kernel Mode: right side says &quot;Read this protected memory!&quot;, left side replies &quot;Here you go, dear :)&quot;. The second, labeled User Mode: right side says &quot;Read this protected memory!&quot;, left side replies &quot;No! Segmentation fault!&quot;" width="1072" height="433"/><p>An example of how processor modes manifest in a real architecture: on x86-64, the current privilege level (CPL) can be read from a register called <code>cs</code> (code segment). Specifically, the CPL is contained in the two <a href="https://en.wikipedia.org/wiki/Bit_numbering" rel="noopener noreferrer" target="_blank">least significant bits</a> of the <code>cs</code> register. Those two bits can store x86-64’s four possible rings: ring 0 is kernel mode and ring 3 is user mode. Rings 1 and 2 are designed for running drivers but are only used by a handful of older niche operating systems. If the CPL bits are <code>11</code>, for example, the CPU is running in ring 3: user mode.</p>
+<!-- nema: retrieval question --><nema-activities for="rings-check"></nema-activities>
+<h2 id="what-even-is-a-syscall">What Even is a Syscall?</h2><p>Programs run in user mode because they can’t be trusted with full access to the computer. User mode does its job, preventing access to most of the computer — but programs need to be able to access I/O, allocate memory, and interact with the operating system <em>somehow</em>! To do so, software running in user mode has to ask the operating system kernel for help. The OS can then implement its own security protections to prevent programs from doing anything malicious.</p><p>If you’ve ever written code that interacts with the OS, you’ll probably recognize functions like <code>open</code>, <code>read</code>, <code>fork</code>, and <code>exit</code>. Below a couple of layers of abstraction, these functions all use <em>system calls</em> to ask the OS for help. A system call is a special procedure that lets a program start a transition from user space to kernel space, jumping from the program’s code into OS code.</p><p>User space to kernel space control transfers are accomplished using a processor feature called <a href="https://en.wikipedia.org/wiki/Interrupt#Software_interrupts" rel="noopener noreferrer" target="_blank"><em>software interrupts</em></a>:</p><ol><li>During the boot process, the operating system stores a table called an <a href="https://en.wikipedia.org/wiki/Interrupt_vector_table" rel="noopener noreferrer" target="_blank"><em>interrupt vector table</em></a> (IVT; x86-64 calls this the <a href="https://en.wikipedia.org/wiki/Interrupt_descriptor_table" rel="noopener noreferrer" target="_blank">interrupt descriptor table</a>) in RAM and registers it with the CPU. The IVT maps interrupt numbers to handler code pointers.</li></ol><img src="images/interrupt-vector-table.png" loading="lazy" style="max-width: 300px; margin: 0 auto;" alt="A image of a table captioned &quot;Interrupt Vector Table&quot;. The first column, labeled with a number sign, has a series of numbers starting at 01 and going to 04. The corresponding second column of the table, labeled &quot;Handler Address&quot;, contains a random 8-byte-long hex number per entry. The bottom of the table has the text &quot;So on and such forth...&quot;" width="555" height="463"/><ol start="2"><li>Then, userland programs can use an instruction like <a href="https://www.felixcloutier.com/x86/intn:into:int3:int1" rel="noopener noreferrer" target="_blank">INT</a> which tells the processor to look up the given interrupt number in the IVT, switch to kernel mode, and then jump the instruction pointer to the memory address stored in the IVT.</li></ol><p>When this kernel code finishes, it uses an instruction like <a href="https://www.felixcloutier.com/x86/iret:iretd:iretq" rel="noopener noreferrer" target="_blank">IRET</a> to tell the CPU to switch back to user mode and return the instruction pointer to where it was when the interrupt was triggered.</p><p>(If you were curious, the interrupt ID used for system calls on Linux is <code>0x80</code>. You can read a list of Linux system calls on <a href="https://man7.org/linux/man-pages/man2/syscalls.2.html" rel="noopener noreferrer" target="_blank">Michael Kerrisk’s online manpage directory</a>.)</p><h3 id="wrapper-apis-abstracting-away-interrupts">Wrapper APIs: Abstracting Away Interrupts</h3><p>Here’s what we know so far about system calls:</p><ul><li>User mode programs can’t access I/O or memory directly. They have to ask the OS for help interacting with the outside world.</li><li>Programs can delegate control to the OS with special machine code instructions like INT and IRET.</li><li>Programs can’t directly switch privilege levels; software interrupts are safe because the processor has been preconfigured <em>by the OS</em> with where in the OS code to jump to. The interrupt vector table can only be configured from kernel mode.</li></ul><p>Programs need to pass data to the operating system when triggering a syscall; the OS needs to know which specific system call to execute alongside any data the syscall itself needs, for example, what filename to open. The mechanism for passing this data varies by operating system and architecture, but it’s usually done by placing data in certain registers or on the stack before triggering the interrupt.</p><p>The variance in how system calls are called across devices means it would be wildly impractical for programmers to implement system calls themselves for every program. This would also mean operating systems couldn’t change their interrupt handling for fear of breaking every program that was written to use the old system. Finally, we typically don’t write programs in raw assembly anymore — programmers can’t be expected to drop down to assembly any time they want to read a file or allocate memory.</p><img src="images/syscall-architecture-differences.png" loading="lazy" style="max-width: 650px; margin: 0 auto;" alt="A drawing captioned &quot;System calls are implemented differently across architectures.&quot; On the left is a smiling CPU receiving some binary and spitting out a filename, file.txt. Separated on the right is a different CPU receiving the same binary data but with a confused and nauseous facial expression." width="1057" height="360"/><p>So, operating systems provide an abstraction layer on top of these interrupts. Reusable higher-level library functions that wrap the necessary assembly instructions are provided by <a href="https://www.gnu.org/software/libc/" rel="noopener noreferrer" target="_blank">libc</a> on Unix-like systems and part of a library called <a href="https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/libraries-and-headers" rel="noopener noreferrer" target="_blank">ntdll.dll</a> on Windows. Calls to these library functions themselves don’t cause switches to kernel mode, they’re just standard function calls. Inside the libraries, assembly code does actually transfer control to the kernel, and is a lot more platform-dependent than the wrapping library subroutine.</p><p>When you call <code>exit(1)</code> from C running on a Unix-like system, that function is internally running machine code to trigger an interrupt, after placing the system call’s opcode and arguments in the right registers/stack/whatever. Computers are so cool!</p>

+<h2 id="the-need-for-speed--lets-get-cisc-y">The Need for Speed / Let’s Get CISC-y</h2><p>Many <a href="https://en.wikipedia.org/wiki/Complex_instruction_set_computer" rel="noopener noreferrer" target="_blank">CISC</a> architectures like x86-64 contain instructions designed for system calls, created due to the prevalence of the system call paradigm.</p><p>Intel and AMD managed not to coordinate very well on x86-64; it actually has <em>two</em> sets of optimized system call instructions. <a href="https://www.felixcloutier.com/x86/syscall.html" rel="noopener noreferrer" target="_blank">SYSCALL</a> and <a href="https://www.felixcloutier.com/x86/sysenter" rel="noopener noreferrer" target="_blank">SYSENTER</a> are optimized alternatives to instructions like <code>INT 0x80</code>. Their corresponding return instructions, <a href="https://www.felixcloutier.com/x86/sysret.html" rel="noopener noreferrer" target="_blank">SYSRET</a> and <a href="https://www.felixcloutier.com/x86/sysexit" rel="noopener noreferrer" target="_blank">SYSEXIT</a>, are designed to transition quickly back to user space and resume program code.</p><p>(AMD and Intel processors have slightly different compatibility with these instructions. <code>SYSCALL</code> is generally the best option for 64-bit programs, while <code>SYSENTER</code> has better support with 32-bit programs.)</p><p>Representative of the style, <a href="https://en.wikipedia.org/wiki/Reduced_instruction_set_computer" rel="noopener noreferrer" target="_blank">RISC</a> architectures tend not to have such special instructions. AArch64, the RISC architecture Apple Silicon is based on, uses only <a href="https://developer.arm.com/documentation/ddi0596/2021-12/Base-Instructions/SVC--Supervisor-Call-" rel="noopener noreferrer" target="_blank">one interrupt instruction</a> for syscalls and software interrupts alike. I think Mac users are doing fine :)</p><hr/><p>Whew, that was a lot! Let’s do a brief recap:</p><ul><li>Processors execute instructions in an infinite fetch-execute loop and don’t have any concept of operating systems or programs. The processor’s mode, usually stored in a register, determines what instructions may be executed. Operating system code runs in kernel mode and switches to user mode to run programs.</li><li>To run a binary, the operating system switches to user mode and points the processor to the code’s entry point in RAM. Because they only have the privileges of user mode, programs that want to interact with the world need to jump to OS code for help. System calls are a standardized way for programs to switch from user mode to kernel mode and into OS code.</li><li>Programs typically use these syscalls by calling shared library functions. These wrap machine code for either software interrupts or architecture-specific syscall instructions that transfer control to the OS kernel and switch rings. The kernel does its business and switches back to user mode and returns to the program code.</li></ul><p>Let’s figure out how to answer my first question from earlier:</p><blockquote><p>If the CPU doesn’t keep track of more than one process and just executes instruction after instruction, why doesn’t it get stuck inside whatever program it’s running? How can multiple programs run at once?</p></blockquote><p>The answer to this, my dear friend, is also the answer to why Coldplay is so popular… clocks! (Well, technically timers. I just wanted to shoehorn that joke in.)</p>
